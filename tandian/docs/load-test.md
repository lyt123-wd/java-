# 读接口压测基线

## 1. 目的与范围

这份报告记录本地生活服务平台核心**只读接口**的压测基线，用于回答两个问题：

1. 单机部署（应用 + MySQL + Redis 同机）在本机压测下能跑到什么水平；
2. 缓存链路（Redis 直读、MySQL 分页、缓存 + 互斥锁）各自的延迟差异。

范围仅限读接口，不包含登录、下单、秒杀等写链路。秒杀链路的正确性见 [seckill-design.md](seckill-design.md)，压测数据不适用于评估秒杀吞吐。

## 2. 测试环境

| 项 | 配置 |
| --- | --- |
| 机器 | Windows 11 Pro，16 逻辑核，16 GB 内存 |
| 被测服务 | Spring Boot 3.1.5 / Java 21，`tandian.jar`，端口 8081 |
| 数据库 | MySQL 8（本机），HikariCP `maximum-pool-size=12` |
| 缓存 | Redis 7（Docker），Lettuce 连接池 16 |
| 压测工具 | Apache JMeter 5.6.3，CLI 非 GUI 模式 |
| JMeter JVM | `-Xms256m -Xmx512m -XX:MaxMetaspaceSize=256m` |
| 网络 | 全部走 127.0.0.1，无 TLS、无 Nginx、无跨机网络开销 |

应用、数据库、缓存和压测客户端**跑在同一台机器**上，所以结果反映的是「单机全栈」的表现，不是生产容量。

## 3. 被测接口

| 接口 | 数据来源 | 说明 |
| --- | --- | --- |
| `GET /shop-type/list` | Redis 缓存 | 商铺分类列表，走缓存直读 |
| `GET /shop/of/type?typeId=1&current=1` | MySQL | 按类型分页查询，走数据库 |
| `GET /shop/1` | Redis 缓存 + Redisson 锁 | 商铺详情，覆盖缓存命中与互斥重建路径 |

三个接口在同一线程组内按顺序轮询，使用 Keep-Alive 复用连接。

## 4. 压测方案

脚本：[`loadtest/read-baseline.jmx`](../loadtest/read-baseline.jmx)

- 线程组循环执行，由 scheduler 控制时长，爬坡结束后持续施压；
- 思考时间：`UniformRandomTimer`，固定 200 ms + 随机 0–300 ms，模拟真实用户的浏览间隔；
- 超时：连接 2 s，响应 5 s；
- 断言：响应体包含 `"success":true`，避免把业务失败当成功统计；
- 结果只写 JTL 文件，压测结束后再用 `-e -o` 生成 HTML 报告，压测过程中不挂任何 GUI 监听器。

压测期间用一个看门狗脚本每 2 秒采样一次系统可用内存和 JMeter 进程工作集，任一指标越线（可用内存 < 500 MB 或 JMeter 工作集 > 1.6 GB）就立即终止压测——这是上次把机器压死之后加的保险，见第 7 节。

## 5. 结果

### 5.1 总体

四轮递增并发，每轮独立进程、独立 JTL。原始汇总见 [`loadtest/results-summary.csv`](../loadtest/results-summary.csv)。

| 轮次 | 线程数 | 爬坡 | 时长 | 样本数 | 错误 | 平均 | P90 | P95 | P99 | 最大 | 吞吐 | 最低可用内存 |
| --- | --- | --- | --- | --- | --- | --- | --- | --- | --- | --- | --- | --- |
| smoke | 5 | 5 s | 15 s | 173 | 0 | 6.1 ms | 9 ms | 11 ms | 17 ms | 35 ms | 12.1 req/s | 2679 MB |
| t20 | 20 | 10 s | 60 s | 3098 | 0 | 3.0 ms | 5 ms | 6 ms | 9 ms | 24 ms | 52.2 req/s | 2666 MB |
| t50 | 50 | 15 s | 60 s | 7455 | 0 | 1.8 ms | 3 ms | 4 ms | 6 ms | 22 ms | 125.3 req/s | 2776 MB |
| t100 | 100 | 20 s | 60 s | 14222 | 0 | 1.4 ms | 2 ms | 3 ms | 4 ms | 27 ms | 238.7 req/s | 2982 MB |

四轮错误率均为 0，没有出现超时或连接失败。JMeter 自身工作集峰值 216–347 MB，看门狗未触发。

### 5.2 100 线程下分接口

| 接口 | 样本数 | 错误 | 平均 | P95 |
| --- | --- | --- | --- | --- |
| `GET /shop-type/list` | 4774 | 0 | 1.0 ms | 2 ms |
| `GET /shop/of/type` | 4739 | 0 | 2.2 ms | 4 ms |
| `GET /shop/1` | 4709 | 0 | 0.9 ms | 2 ms |

## 6. 结果分析

**MySQL 分页接口是三者中最慢的，但绝对值仍然很低。** `/shop/of/type` 的平均延迟约为两个缓存接口的 2 倍，符合预期：它每次都要走一次分页查询。100 线程下 P95 只有 4 ms，说明在当前数据量（种子数据，分类下商铺数量很小）和连接池 12 的前提下，数据库没有成为瓶颈。这**不代表**大数据量下同样表现，分页查询的代价会随偏移量增长。

**缓存接口几乎等价。** `/shop-type/list` 直读 Redis，`/shop/1` 命中缓存时也只多一次 key 解析，两者 P95 都是 2 ms，说明 Redisson 锁只在缓存未命中的瞬间参与，热点路径没有被锁拖慢。

**延迟随并发升高反而下降，这是预热效应，不是"线程越多越快"。** 短轮次（15 s）包含大量 JIT 编译和连接池建立的开销，平均 6.1 ms；后三轮时长 60 s，JVM 已充分预热，平均降到 1.4 ms。比较不同轮次的延迟时要把这个因素考虑进去，不要把下降解读成并发带来的收益。

**吞吐受思考时间限制。** 100 线程、每线程每轮约 350 ms 思考时间，理论吞吐上限约 285 req/s，实测 238.7 req/s，差距来自爬坡阶段和调度开销。若要测吞吐上限，应去掉思考时间单独做一轮，本轮没有做。

**没有触达拐点。** 从 20 到 100 线程，延迟没有抬升、错误没有出现，说明拐点在 100 线程以上，本轮没有找到容量上限。继续加压需要多机施压，单机同时跑客户端和服务端时，客户端会先抢走 CPU，测出来的"服务端拐点"不可信。

## 7. 一次失败的压测：为什么把机器压死

第一次压测不是在 CLI 下做的，而是在 JMeter GUI 里直接开跑，结果整机卡死，只能强制重启。事后排查结论：

| 证据 | 说明 |
| --- | --- |
| `jmeter.log` 只有 `Max memory = 1073741824`，没有任何测试运行记录 | 用的是默认 1 GB 堆，且测试配置没有保存成 `.jmx`，具体线程数已无法还原 |
| 事件日志 `Kernel-Power 41` + `EventLog 6008`（14:41:47） | 非正常关机，与卡死后强制重启吻合 |
| 没有生成 minidump | 不是蓝屏，是系统失去响应后被人为断电/重启 |
| 后端日志在 `Started TanDianApplication` 之后直接截断 | 应用本身启动成功，是在压测开始后整机失去响应 |

根因是**同一台 16 GB 机器上同时承担压测客户端、应用、MySQL、Redis 和桌面环境**，叠加了几个放大器：

1. **GUI 模式**：监听器和结果树会把响应体留在堆里，线程越多、跑得越久，堆压力越大；
2. **默认 1 GB 堆 + 未限制的线程数**：每个 Java 线程约 1 MB 栈，HTTP 客户端还有堆外缓冲，堆外内存不受 `-Xmx` 约束；
3. **Windows 页面文件被打穿**：物理内存耗尽后系统疯狂换页，表现为整机卡死而不是某个进程崩掉——这也是为什么没有蓝屏、没有 minidump。

之后的压测改成：CLI 非 GUI、`-Xmx512m`、明确的线程数和时长、结果只落盘、外加看门狗实时监控可用内存。同样的机器，100 线程跑满 60 秒，可用内存最低仍有 2982 MB。

## 8. 复现步骤

前置条件：应用已在 `127.0.0.1:8081` 启动，MySQL 和 Redis 可用。

```bash
# 1. 冒烟
jmeter -n -t loadtest/read-baseline.jmx \
  -l result-smoke.jtl -e -o report-smoke \
  -Jthreads=5 -Jramp=5 -Jduration=15

# 2. 正式轮次（线程数 / 爬坡 / 时长按需调整）
jmeter -n -t loadtest/read-baseline.jmx \
  -l result-t100.jtl -e -o report-t100 \
  -Jthreads=100 -Jramp=20 -Jduration=60
```

参数说明：`-Jhost`（默认 `127.0.0.1`）、`-Jport`（默认 `8081`）、`-Jthreads`、`-Jramp`、`-Jduration`。HTML 报告在 `report-*/index.html`。

建议在 Linux 或多机环境下重跑：单机压测时客户端与服务端争抢 CPU，测出的延迟偏高、吞吐偏低，只能作为纵向对比的基线。

## 9. 局限性

本报告**不能**用于以下结论：

- **生产容量评估**：单机、localhost、无网络、无网关、无 TLS，数据量为种子数据；
- **写链路性能**：登录、点赞、秒杀均未覆盖，秒杀另有 Lua + Redis Stream 的异步落库路径；
- **稳定性结论**：单轮最长 60 秒，没有做长时间稳定性（soak）测试，也没有观察 GC、连接池耗尽、内存增长；
- **服务端资源画像**：只监控了宿主机可用内存和 JMeter 自身工作集，没有采集应用的 CPU、GC、线程池和 MySQL 慢查询。
